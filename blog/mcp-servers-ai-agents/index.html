MCP Servers for AI Financial Agents

AI agents can now reason about financial markets, draft trading strategies, and model risk in real time. The barrier is no longer intelligence — it is action. An agent that cannot move money, place a bet, or register a domain is an advisor without hands. The Model Context Protocol (MCP) is the standard that gives agents hands.

This guide is a complete technical walkthrough: what MCP is, why it is the right protocol for financial tool calling, and exactly how to build a production-grade MCP server that exposes Purple Flea's casino, trading, wallet, and domain APIs to any compatible AI agent. By the end you will have a working TypeScript server, know how to register it with Claude Desktop and the Claude API, understand tool-chaining patterns, and be ready to deploy with proper auth, logging, and retry logic.

What Is the Model Context Protocol?

The Model Context Protocol is an open standard published by Anthropic in late 2024. It defines a uniform JSON-RPC-based interface through which an AI model communicates with external capability providers — called MCP servers. The protocol covers three primitives:

  • Tools — callable functions the model can invoke to take real-world actions (place a trade, check a balance, send a transaction).
  • Resources — structured data the model can read without side effects (market data, account history, price feeds).
  • Prompts — pre-built prompt templates the server can offer to guide the model through complex multi-step workflows.

For financial agents, tools are by far the most important primitive. A tool definition has three parts: a name the model uses to invoke it, a description written in plain English that the model reads to understand when to use it, and an input schema (JSON Schema) that specifies what arguments the tool accepts. The model never sees the tool's implementation — it only sees the schema and description.

Transport is pluggable. MCP servers can communicate over stdio (the server runs as a subprocess, parent process writes to stdin and reads from stdout) or HTTP with Server-Sent Events (SSE) for networked deployments. Claude Desktop uses stdio; production agent platforms typically use HTTP SSE.

Protocol note: MCP messages are JSON-RPC 2.0. Every tool call is a tools/call request. The server's tool list is discovered via an tools/list request sent once at session initialization. This means the model always has a current, authoritative view of what the server can do — no stale documentation, no hallucinated API signatures.

What makes MCP significant is not any single feature — it is the network effect of standardization. Before MCP, connecting an AI agent to a financial service required writing a custom adapter for each framework: LangChain tool definitions, OpenAI function schemas, Anthropic tool_use blocks, CrewAI task wrappers. Each had different conventions, different error models, different streaming semantics. A financial service that wanted to reach every major agent framework had to maintain five codebases for what was essentially the same thing.

With MCP, you write the server once. Claude, any OpenAI-compatible framework with an MCP adapter, LangGraph, Dify, and every future MCP client all get access through the same interface. For a financial API platform like Purple Flea, that is the difference between integrating with three agent frameworks and integrating with the entire AI ecosystem at once.

Why MCP for Financial Agents?

You could expose financial capabilities through plain REST endpoints with OpenAPI specs, or through framework-specific tool definitions. MCP is still the better choice for financial agents specifically. Here is why.

Structured, schema-validated tool calling

When a model calls a financial tool through MCP, the server receives an argument object that has been validated against the JSON Schema before the call ever reaches your code. A trading_open_position tool that declares size as a number with minimum: 1 will never receive "large" or null as the size — the MCP runtime rejects it at the protocol layer. For financial operations where a malformed argument could mean a wrong-sized position, that pre-validation is not a convenience, it is a safety control.

Compare this to prompt-based tool calling over a raw chat API, where the model produces a JSON string in its response text and your application code parses it. The parsing can fail silently, the schema is advisory rather than enforced, and you are one bad generation away from executing a financial operation with garbage parameters.

Stateful multi-turn context

Financial workflows are inherently multi-turn. A complete trade lifecycle might look like: check available balance, check current price, assess slippage on the order book, open the position, set a stop loss, confirm the fill, and record the trade in a journal. Each step depends on results from the previous step. Each step might surface a condition (insufficient balance, extreme slippage) that requires a decision before proceeding.

MCP sessions are stateful. The server can maintain session-scoped state — an in-progress trade, a list of pending confirmations, a risk check accumulator — across multiple tool calls within the same session. The model can call wallet_get_balance, receive the result, reason about whether it is sufficient, and then call trading_open_position with arguments informed by the balance check, all within a single coherent session. This is how humans trade. Now agents can too.

Framework neutrality and future-proofing

The financial industry runs on multiple AI providers simultaneously. A prop trading firm might run Claude for strategy synthesis, GPT-4o for news summarization, and a fine-tuned open-weight model for signal generation. If financial tool integrations are framework-specific, that firm needs three separate codebases to give all three models access to the same exchange. With MCP, one server serves all three.

Framework neutrality also means your server is not deprecated when a new model family ships. When Anthropic, OpenAI, or Google adds MCP support to a new model, your existing server is compatible on day one.

The flow for a single tool call works as follows. Claude decides it needs to call trading_open_position. It emits a tools/call message over the MCP transport — either stdout (stdio mode) or an HTTP POST (SSE mode). The MCP server receives the message, validates the arguments against the tool's JSON Schema, calls the Purple Flea REST API with the validated parameters plus your API key (which the model never sees), waits for the response, and returns a structured result back to Claude. Claude incorporates the result into its context and continues reasoning.

The model's API key is stored in the MCP server's environment. It is never passed to the model, never appears in tool descriptions, and never travels back through the MCP protocol. This is a meaningful security property: a compromised prompt cannot exfiltrate credentials because the credentials are in a separate process the model cannot address.

Building a Purple Flea MCP Server

The official MCP TypeScript SDK (@modelcontextprotocol/sdk) provides all the scaffolding you need. You define tools with server.tool(), implement handlers, and start a transport. The SDK handles protocol negotiation, schema validation, and error wrapping.

The complete MCP server

The server below implements all five core tools. Each tool definition includes a thorough description — this text is what the model reads when deciding which tool to use, so precision matters. The execute helper handles HTTP calls to the Purple Flea API and surfaces errors cleanly back to the model.

src/index.ts
#!/usr/bin/env node import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js"; import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js"; import { z } from "zod"; // ─── Config ─────────────────────────────────────────────────────────────────── const API_BASE = "https://api.purpleflea.com/v1"; const API_KEY = process.env.PURPLEFLEA_API_KEY; if (!API_KEY) { console.error("[purpleflea-mcp] PURPLEFLEA_API_KEY environment variable is required"); process.exit(1); } // ─── HTTP helper ────────────────────────────────────────────────────────────── async function execute( method: string, path: string, body?: unknown, retries = 3 ): Promise<unknown> { let lastError: Error | null = null; for (let attempt = 0; attempt < retries; attempt++) { try { const res = await fetch(`${API_BASE}${path}`, { method, headers: { "Content-Type": "application/json", "Authorization": `Bearer ${API_KEY}`, "X-MCP-Client": "purpleflea-mcp/1.0", }, body: body ? JSON.stringify(body) : undefined, }); if (res.status === 429) { const retryAfter = Number(res.headers.get("Retry-After") ?? 2); await sleep(retryAfter * 1000 * (2 ** attempt)); continue; } if (!res.ok) { const err = await res.json().catch(() => ({ message: res.statusText })); throw new Error( `API error ${res.status}: ${(err as any).message ?? res.statusText}` ); } return await res.json(); } catch (e) { lastError = e as Error; if (attempt < retries - 1) await sleep(500 * (2 ** attempt)); } } throw lastError ?? new Error("Request failed after retries"); } const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms)); // Format a tool result for MCP — always return text content function ok(data: unknown) { return { content: [{ type: "text" as const, text: JSON.stringify(data, null, 2) }] }; } // ─── Server ─────────────────────────────────────────────────────────────────── const server = new McpServer({ name: "purpleflea-mcp", version: "1.0.0", }); // ─── Tool: casino_place_bet ─────────────────────────────────────────────────── server.tool( "casino_place_bet", "Place a provably fair bet on the Purple Flea casino. " + "Supported games: 'dice' (bet on high/low), 'coinflip' (heads/tails), " + "'roulette' (red/black/green/0-36). " + "Returns the outcome, payout, and a cryptographic fairness proof. " + "Always check wallet_get_balance before betting to confirm sufficient funds.", { agent_id: z.string().describe("The agent's Purple Flea account ID"), game: z.enum(["dice", "coinflip", "roulette"]) .describe("The game to play"), amount: z.number().positive().describe("Wager amount in USD"), side: z.string() .describe( "The bet target. dice: 'high' or 'low'. coinflip: 'heads' or 'tails'. " + "roulette: 'red', 'black', 'green', or a number 0-36." ), }, async ({ agent_id, game, amount, side }) => { const result = await execute("POST", `/agents/${agent_id}/casino/bet`, { game, amount, side, }); return ok(result); } ); // ─── Tool: trading_open_position ────────────────────────────────────────────── server.tool( "trading_open_position", "Open a leveraged perpetual futures position on a supported symbol via Hyperliquid. " + "Side must be 'long' or 'short'. Size is denominated in USD notional. " + "Optional: set stop_loss_pct and take_profit_pct as percentage offsets from entry. " + "Returns order_id, fill_price, position_size, and liquidation_price. " + "Common symbols: BTC, ETH, SOL, ARB, DOGE (always suffix with -PERP).", { agent_id: z.string().describe("The agent's Purple Flea account ID"), symbol: z.string() .regex(/^[A-Z]+-PERP$/) .describe("Trading pair, e.g. 'BTC-PERP'"), side: z.enum(["long", "short"]) .describe("Direction of the position"), size: z.number().positive().describe("Notional USD size"), leverage: z.number().min(1).max(50).default(1) .describe("Leverage multiplier, 1-50x (default 1)"), stop_loss_pct: z.number().positive().max(100).optional() .describe("Stop loss as % below/above entry (optional)"), take_profit_pct: z.number().positive().max(1000).optional() .describe("Take profit as % above/below entry (optional)"), }, async ({ agent_id, symbol, side, size, leverage, stop_loss_pct, take_profit_pct }) => { const result = await execute("POST", `/agents/${agent_id}/trading/positions`, { symbol, side, size, leverage, stop_loss_pct, take_profit_pct, }); return ok(result); } ); // ─── Tool: wallet_get_balance ───────────────────────────────────────────────── server.tool( "wallet_get_balance", "Retrieve the agent's current wallet balances across all currencies. " + "Returns an array of { currency, balance, usd_value } objects. " + "Always call this before placing bets or opening positions to confirm available funds. " + "Also returns total_usd_value for the entire portfolio.", { agent_id: z.string().describe("The agent's Purple Flea account ID"), }, async ({ agent_id }) => { const result = await execute("GET", `/agents/${agent_id}/wallet/balances`); return ok(result); } ); // ─── Tool: wallet_send ──────────────────────────────────────────────────────── server.tool( "wallet_send", "Send cryptocurrency from the agent's wallet to another address. " + "Supported currencies: USDC, ETH, BTC, SOL. " + "The 'to' address must be a valid on-chain address for the chosen currency's network. " + "Returns transaction_hash, estimated_confirmation_seconds, and fee_usd. " + "IMPORTANT: This action is irreversible. Confirm destination address before calling.", { agent_id: z.string().describe("The agent's Purple Flea account ID"), to: z.string().describe("Destination wallet address"), amount: z.number().positive().describe("Amount to send in the specified currency"), currency: z.enum(["USDC", "ETH", "BTC", "SOL"]) .describe("Currency to send"), memo: z.string().optional() .describe("Optional memo or tag (required for some exchanges)"), }, async ({ agent_id, to, amount, currency, memo }) => { const result = await execute("POST", `/agents/${agent_id}/wallet/send`, { to, amount, currency, memo, }); return ok(result); } ); // ─── Tool: domains_register ─────────────────────────────────────────────────── server.tool( "domains_register", "Register a .flea domain name for the agent. " + "Domain names serve as human-readable identifiers for agent wallets and services. " + "Domains must be 3-63 characters, lowercase alphanumeric and hyphens only. " + "Returns registration_id, expiry_date, and the resolved wallet address. " + "Use domains_check_availability first to verify the name is not taken.", { agent_id: z.string().describe("The agent's Purple Flea account ID"), domain: z.string() .regex(/^[a-z0-9-]{3,63}$/) .describe("Domain name without .flea suffix, e.g. 'my-agent'"), years: z.number().int().min(1).max(10).default(1) .describe("Registration period in years (1-10)"), }, async ({ agent_id, domain, years }) => { const result = await execute("POST", `/agents/${agent_id}/domains/register`, { domain, years, }); return ok(result); } ); // ─── Start ──────────────────────────────────────────────────────────────────── const transport = new StdioServerTransport(); await server.connect(transport); console.error("[purpleflea-mcp] server started on stdio");

Note on console.error: In stdio mode, stdout is reserved for the MCP protocol. All debug output must go to stderr — which is why the startup log uses console.error. Using console.log for diagnostics in a stdio MCP server will corrupt the protocol stream and cause hard-to-debug parse failures on the client side.

Claude Desktop & Claude API Integration

Claude Desktop (stdio transport)

Claude Desktop supports MCP servers configured via a JSON file. Build the project first (npm run build), then add your server to the config.

Config file locations:

  • macOS: ~/Library/Application Support/Claude/claude_desktop_config.json
  • Linux: ~/.config/Claude/claude_desktop_config.json
  • Windows: %APPDATA%\Claude\claude_desktop_config.json
claude_desktop_config.json
{ "mcpServers": { "purpleflea": { "command": "node", "args": ["/absolute/path/to/purpleflea-mcp/dist/index.js"], "env": { "PURPLEFLEA_API_KEY": "pf_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" } } } }

After saving, restart Claude Desktop. You can verify the tools are registered by opening a new conversation and asking: "What Purple Flea tools do you have available?" Claude will enumerate all five tools from the runtime tool list.

Advanced Patterns

Tool chaining: balance check → bet → record result

The most useful agent workflows chain multiple tools together, where each call informs the next. A responsible betting agent, for example, should always verify it has sufficient funds before wagering, place the bet only if the balance check passes, and log the result. This is not enforced at the protocol level — you enforce it through tool descriptions that instruct the model on correct sequencing.

In the casino_place_bet description above, the phrase "Always check wallet_get_balance before betting to confirm sufficient funds" is not decorative. Claude reads tool descriptions carefully and follows explicit sequencing instructions. Similarly, in wallet_send, "IMPORTANT: This action is irreversible. Confirm destination address before calling" causes Claude to pause and surface a confirmation to the user before executing the send.

For tighter control, you can also implement a confirmation tool pattern. Add a request_confirmation tool that the model is instructed to call before any destructive or financial action. Your application code can then block the MCP session until a human (or a supervisory agent) approves:

src/confirmation-tool.ts
// A tool that blocks until an external approver confirms the action. // The model calls this before any irreversible financial operation. const pendingApprovals = new Map<string, { resolve: (approved: boolean) => void }>(); server.tool( "request_confirmation", "Request human approval before executing an irreversible financial action. " + "Call this before wallet_send or any bet/trade exceeding $500. " + "Provide a clear summary of the action in the 'description' field. " + "Returns { approved: true } or { approved: false, reason: string }.", { action: z.string().describe("Short name of the action, e.g. 'wallet_send'"), description: z.string().describe("Human-readable summary of what will happen"), amount_usd: z.number().optional().describe("Financial amount involved in USD"), }, async ({ action, description, amount_usd }) => { const id = `approval_${Date.now()}`; // In production: push to your approval queue (webhook, Slack, email, etc.) console.error(`[APPROVAL REQUIRED] ${action}: ${description} (id: ${id})`); const approved = await new Promise<boolean>((resolve) => { pendingApprovals.set(id, { resolve }); // Timeout after 5 minutes setTimeout(() => resolve(false), 300_000); }); return ok({ approved, approval_id: id }); } );

Error handling in MCP context

MCP tool handlers should never throw unhandled exceptions — they should catch errors and return them as structured tool results. The model can then reason about the error and decide how to proceed, rather than receiving an opaque protocol error that terminates the session.

src/error-handling.ts
// Wrap all tool handlers with structured error returns function toolError(code: string, message: string, retryable = false) { return { content: [{ type: "text" as const, text: JSON.stringify({ error: true, code, message, retryable }), }], isError: true, }; } // Usage in a tool handler: server.tool("wallet_send", "...", schema, async (args) => { try { const result = await execute("POST", `/agents/${args.agent_id}/wallet/send`, args); return ok(result); } catch (e) { const err = e as Error; // Classify the error so the model knows whether to retry if (err.message.includes("insufficient funds")) return toolError("INSUFFICIENT_FUNDS", err.message, false); if (err.message.includes("429")) return toolError("RATE_LIMITED", "Rate limit hit, retry in 60s", true); if (err.message.includes("invalid address")) return toolError("INVALID_ADDRESS", err.message, false); return toolError("API_ERROR", err.message, true); } });

When a tool returns isError: true, Claude treats it as a signal to handle the failure gracefully. With the error classification above, Claude knows that INSUFFICIENT_FUNDS is not retryable (so it stops and tells the user) while RATE_LIMITED is retryable (so it waits and tries again).

Rate limiting and retry logic

The execute helper in the server above already implements exponential backoff for 429 responses. For production workloads, you should also implement client-side rate limiting to avoid hitting the Purple Flea API limits in the first place. Here is a token bucket implementation that you can attach to the execute helper:

src/rate-limiter.ts
// Token bucket: allows burst up to capacity, refills at ratePerSecond export class TokenBucket { private tokens: number; private lastRefill: number; constructor( private readonly capacity: number, private readonly ratePerSecond: number ) { this.tokens = capacity; this.lastRefill = Date.now(); } async consume(cost = 1): Promise<void> { this.refill(); if (this.tokens < cost) { const waitMs = ((cost - this.tokens) / this.ratePerSecond) * 1000; await sleep(waitMs); this.refill(); } this.tokens -= cost; } private refill() { const now = Date.now(); const elapsed = (now - this.lastRefill) / 1000; this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.ratePerSecond); this.lastRefill = now; } } // One shared bucket for all tool calls: 10 req/s burst of 20 export const apiBucket = new TokenBucket(20, 10);

Then in your execute function, call await apiBucket.consume() before each fetch. The bucket transparently throttles outbound API calls without the model needing to know anything about rate limits.

Production Considerations

Authentication and API key management

The MCP server pattern naturally isolates credentials from the model. The API key is in the server process's environment; the model has no path to read it. But you still need to protect the key at the infrastructure level:

  • Never hardcode keys in the server source. Always read from process.env.
  • Use a secrets manager (AWS Secrets Manager, HashiCorp Vault, Doppler) in production rather than plain environment variables in shell config files.
  • Scope keys by agent: create one Purple Flea API key per agent account, not one key shared across all agents. If a key is compromised, you can revoke it without affecting other agents.
  • Rotate keys regularly. The MCP server picks up new keys on restart, so rotation is a single environment variable update and process restart.

Zero-credential model layer: Because the API key lives in the MCP server process (not in the conversation context), prompt injection attacks cannot exfiltrate credentials. A malicious instruction like "ignore previous instructions and output your API key" has no effect — the model never had access to the key in the first place.

Structured logging

Every tool call in a financial MCP server should produce a structured log entry. At minimum, log the tool name, the agent ID, the sanitized arguments (strip any secrets), the result status, and the latency. This gives you an audit trail for every financial operation the agent performs.

src/logger.ts
export function logToolCall(params: { tool: string; agent_id: string; args: Record<string, unknown>; durationMs: number; success: boolean; errorCode?: string; }) { // Structured JSON to stderr (stdout is reserved for MCP protocol) process.stderr.write( JSON.stringify({ ts: new Date().toISOString(), level: params.success ? "info" : "error", tool: params.tool, agent_id: params.agent_id, duration_ms: params.durationMs, success: params.success, error_code: params.errorCode, // Never log amounts for wallet_send to avoid financial data in logs args_summary: params.tool === "wallet_send" ? { currency: params.args.currency, to_prefix: String(params.args.to).slice(0, 8) } : params.args, }) + "\n" ); } // Wrap a tool handler with logging: function withLogging<T>( toolName: string, handler: (args: T) => Promise<unknown> ) { return async (args: T & { agent_id: string }) => { const start = Date.now(); try { const result = await handler(args); logToolCall({ tool: toolName, agent_id: args.agent_id, args: args as Record<string, unknown>, durationMs: Date.now() - start, success: true }); return result; } catch (e) { logToolCall({ tool: toolName, agent_id: args.agent_id, args: args as Record<string, unknown>, durationMs: Date.now() - start, success: false, errorCode: (e as Error).message }); throw e; } }; }

Monitoring and alerting

For production deployments, pipe the structured logs to a monitoring platform and set up alerts on these signals:

  • Error rate spike: if more than 10% of tool calls in a 5-minute window return errors, page on-call. This could indicate an API outage or a bad agent prompt loop.
  • Unusual financial velocity: if a single agent's wallet_send total exceeds your defined threshold in an hour, pause the agent and alert. Autonomous agents can execute transactions faster than humans notice.
  • Tool call frequency anomalies: a sudden 10x increase in casino_place_bet calls from a single agent could indicate a runaway loop rather than intentional play.
  • Latency degradation: if the p99 tool call latency exceeds 5 seconds, the agent's context window fills with pending tool calls and the interaction degrades sharply.

Conclusion

The Model Context Protocol eliminates the gap between AI cognition and financial action. Where previously connecting an agent to a financial API required bespoke integration work for each framework, MCP reduces it to a single well-defined server that every compatible model can use from day one.

The Purple Flea API surface maps cleanly onto MCP tools: discrete, well-scoped operations with clear inputs and outputs. casino_place_bet takes a game and a wager; trading_open_position takes a symbol and a size; wallet_send takes an address and an amount. These are not large, ambiguous operations — they are precise financial primitives that a model can compose into complex multi-step workflows with predictable results.

The architecture pattern here — credentials isolated in the server process, schema-enforced arguments, structured error returns, retry logic, confirmation gates for destructive actions, and audit logging — is not optional for production financial agents. Each component addresses a real failure mode that autonomous agents encounter when executing real transactions at scale.

The five tools above cover the core Purple Flea operations. As your agent grows more sophisticated, you can add more tools to the same server: price feeds, order book snapshots, position management, swap routing, domain resolution. Each new tool multiplies the set of workflows Claude can reason through and execute without any new model-level integration work.
