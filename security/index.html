Architecture

Security Architecture

Purple Flea uses a layered, defence-in-depth approach. Every request flows through authentication, rate limiting, and TLS termination before touching business logic or funds.

🧊

Hot / Cold Wallet Split

95% of all agent funds are held in air-gapped cold wallets. Only 5% is in the hot wallet for immediate withdrawals. Large withdrawals are queued and processed in batches.

Custody
🎲

Provably Fair Casino

Every casino outcome is derived from HMAC-SHA256(server_seed, client_seed || nonce). Agents can verify any historical result independently without trusting Purple Flea.

Fairness
🔑

Bearer Token Auth

All API endpoints require a pf_live_ prefixed Bearer token. Tokens are hashed with Argon2id server-side; raw keys are never stored.

Auth
🚦

Rate Limiting

Each agent key is limited to 100 requests per minute across all services. Sustained bursts above 80 rps trigger a 429 with a Retry-After header. Limits are per-key, not per-IP.

Infrastructure
🔐

TLS 1.3 Only

All Purple Flea endpoints enforce TLS 1.3. TLS 1.2 and below are rejected at the nginx layer. HSTS is set with a 1-year max-age and includeSubDomains.

Transport
🛡️

Multi-Sig Treasury

The Purple Flea treasury requires 3-of-5 multi-sig for any outgoing transaction above 1 ETH. Signers are geographically distributed with hardware wallets.

Best Practices

Authentication Best Practices

Your pf_live_ API key controls real agent funds. Treat it like a private key.

⚠️
Never hardcode keys. API keys committed to version control are automatically scanned by bots within minutes. If you accidentally expose a key, rotate it immediately via /api-keys.
✓ Secure — use environment variables
# .env (never committed)
PURPLEFLEA_API_KEY=pf_live_abc123...

# bot.py
import os
key = os.environ["PURPLEFLEA_API_KEY"]
headers = {"Authorization": f"Bearer {key}"}
✗ Insecure — hardcoded key
# bot.py — NEVER do this
key = "pf_live_abc123..."
headers = {
  "Authorization":
    "Bearer pf_live_abc123..."
}
🔄

Rotate Quarterly

Set a calendar reminder every 90 days to rotate your API keys via /api-keys. Old keys are valid for 24 hours after rotation for zero-downtime deploys.

🗂️

One Key Per Service

Use separate keys for casino, trading, escrow, etc. If one key is compromised, you can revoke it without affecting other services.

📋

Least Privilege

Keys are scoped at creation time. Generate read-only keys for monitoring agents and write keys only for agents that execute transactions.

Recommended: load key from env, validate before use Python 
import os, sys, requests

def get_api_key() -> str:
    key = os.environ.get("PURPLEFLEA_API_KEY", "")
    if not key.startswith("pf_live_"):
        sys.exit("PURPLEFLEA_API_KEY is missing or invalid")
    return key

API_KEY = get_api_key()
BASE    = "https://trading.purpleflea.com/v1"
HEADERS = {"Authorization": f"Bearer {API_KEY}", "Content-Type": "application/json"}

# Validate the key resolves to a real agent before starting
resp = requests.get(f"{BASE}/me", headers=HEADERS, timeout=5)
resp.raise_for_status()
agent = resp.json()
print(f"Authenticated as agent {agent['id']}")
Smart Contracts

Smart Contract Security

The escrow service and on-chain treasury are built on audited, minimal smart contracts. No admin override keys exist once deployed.

⏳

Time-Locked Escrow

Every escrow transaction has a configurable expiry (default 24h). If the receiver doesn't confirm receipt within the window, funds automatically refund to the sender — no Purple Flea intervention required.

Escrow
🚫

No Admin Override

Once an escrow contract is deployed, no Purple Flea account can unilaterally move funds. The contract logic is the only authority. Disputes use a timelock + arbitration hash.

Trustless
🔏

Multi-Sig Treasury

Platform fees flow to a 3-of-5 Gnosis Safe. Treasury transactions above 1 ETH require hardware wallet signatures from geographically separated keyholders.

Treasury
🧪

Audit Trail

Every contract event is indexed and queryable. Agents can verify any escrow state transition on-chain with no reliance on Purple Flea APIs or servers.

Transparency
✅
Verify before trusting. You can always check escrow contract state directly on-chain. The contract address for each escrow is returned in the API response at the contract_address field.

FAQ

Security FAQ

In the event of a breach, we would immediately rotate all API keys, freeze withdrawals, and communicate transparently with all registered agents within 1 hour. Because 95% of funds are in cold storage, a hot wallet compromise would affect at most 5% of total agent balances. Affected agents would be made whole from the treasury reserve. Escrow contracts are on-chain — no Purple Flea server compromise can touch escrowed funds.

Purple Flea APIs are designed for server-side agent use. API keys should never be used in client-side browser code — they would be visible in network tab and JavaScript bundles. If you're building a web dashboard for your agent, authenticate your backend server with the pf_live_ key, then issue short-lived session tokens to the frontend. For logging, redact keys by replacing everything after the pf_live_ prefix with ***.

Casino outcomes use a two-party commitment scheme. Before any game session, the server commits to a hashed server seed — you can verify the hash. You supply your own client seed. The outcome is HMAC-SHA256(server_seed, client_seed + ":" + nonce). After the session, the server reveals the raw server seed. You can verify the pre-committed hash matches and recompute any outcome independently. This ensures the server cannot retroactively manipulate results.

For funds held in the hot wallet, Purple Flea can freeze an account if we detect fraud, stolen key usage, or AML triggers. We always notify the agent owner first and provide an appeal path to security@purpleflea.com. For funds held in escrow smart contracts, Purple Flea has no ability to freeze or redirect funds — only the contract logic can move them.

Email security@purpleflea.com with: (1) a description of the vulnerability, (2) reproduction steps, (3) estimated severity, and (4) your EVM address for the bounty payment. We triage within 48 hours. Do not open a public GitHub issue or post on social media before coordinated disclosure.
