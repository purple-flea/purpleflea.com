1. Compound v2 vs v3 (Comet): Architecture Deep Dive

Compound Finance has gone through two major architectural generations, each with meaningfully different mechanics that agents must understand before deploying capital. The wrong mental model leads to mismatched strategy selection — a v2 approach naively applied to v3 (Comet) will underperform or fail entirely.

Compound v2: The Pooled-Asset Model

In Compound v2, every supported asset has its own isolated cToken contract (cETH, cUSDC, cDAI, etc.). When you supply 1,000 USDC, the protocol mints a proportional amount of cUSDC tokens that accrue interest continuously via an ever-increasing exchange rate. The core accounting rule is:

cToken_balance × exchangeRate = underlying_balance

The exchange rate starts at 0.02 and increases monotonically as interest accrues. An agent holding cUSDC does not need to manually claim interest — it is automatically embedded in the exchange rate. This design is elegant for long-hold positions but creates complexity for agents that need to compute real-time underlying balances across many simultaneous positions.

Borrowing in v2 works across all supplied assets simultaneously. The protocol aggregates collateral value across all cToken positions (weighted by each asset's collateral factor) and allows borrowing up to that weighted value across any supported asset. This creates a cross-asset risk pool: a bad debt event in one asset can trigger liquidation of collateral in a completely different one.

Compound III (Comet): The Base Asset Model

Compound III, deployed starting in 2022 and now spanning multiple chains, abandons the pooled multi-asset model entirely. Each Comet deployment is defined by a single base asset (typically USDC or ETH). You can only borrow that base asset. All other assets serve purely as collateral — they earn no yield when supplied to Comet. This is the most important architectural difference agents must internalize:

Compound v2

Supply any asset, earn yield on it. Borrow any asset. Cross-collateral risk. COMP distributed to both suppliers and borrowers. Pooled liquidity per cToken.

Compound III (Comet)

Supply base asset (USDC/ETH) to earn yield. Collateral assets earn NO yield. Only borrow the base asset. Isolated per-deployment. COMP rewards configurable per market by governance.

In Comet, the Comet.sol contract replaces the entire suite of cToken contracts. All interactions flow through a single entry point. Key implications for agents:

  • Capital efficiency trade-off: Non-base collateral (ETH, WBTC, cbETH) sits idle in Comet. Agents supplying ETH as collateral to borrow USDC sacrifice ETH staking yield. This opportunity cost must be factored into net position APY calculations.
  • Interest model: Comet uses a curve-based interest rate model with supply and borrow rates derived from utilization, governed by parameters (supplyKink, borrowKink, slope parameters) that the DAO can update via proposal.
  • Collateral factors vs. liquidation factors: Each collateral asset has both a borrowCollateralFactor (maximum LTV for new borrows) and a liquidateCollateralFactor (threshold below which liquidation becomes possible). The gap between them is your safety cushion — and it varies meaningfully by asset.
Key Insight for Agents: Comet's base asset supply earns a variable supply APR paid directly by borrowers plus any COMP rewards allocated by governance. When utilization is high, supply APR can spike significantly above the kink point. Agents should monitor getSupplyRate(utilization) and getBorrowRate(utilization) view functions in real time to detect entry and exit opportunities.

2. COMP Token Rewards and Yield Boosting

COMP is distributed to protocol participants as an incentive mechanism. The distribution schedule has evolved significantly: in v2, COMP flowed to both suppliers and borrowers in proportion to the interest they generated; in Comet (v3), reward distribution is configurable per deployment and governed by the DAO, enabling targeted incentivization of specific behaviors such as only rewarding USDC borrowers on a specific chain.

V2 COMP Distribution Mechanics

In v2, the Comptroller contract tracks a global compSpeed per market (split between supply-side and borrow-side). Each time a market action occurs (mint, redeem, borrow, repay), the protocol updates an index:

compIndex = compIndex + (deltaBlocks * compSpeed / totalSupply)
accrued[user] += (compIndex - userIndex) * cToken_balance

COMP accrual only updates when the index is refreshed. Agents running long-lived positions that never interact with the protocol will see stale accrued values in compAccrued[address] until they trigger an update via a call to claimComp(address) or any market interaction. Build this into your accounting pipeline — stale accrual reads will undercount earned COMP.

Comet COMP Reward Mechanics

In Comet, rewards are tracked in the CometRewards contract. Each Comet instance can have independent reward configurations. The RewardConfig struct specifies the reward token (usually COMP), a rescale factor for precision, and whether rewards track total borrows or total supply. Agents claim via:

// Solidity: claim COMP for an account from Comet
CometRewards(rewardsAddr).claim(
    cometProxy,   // which Comet deployment
    recipient,    // who receives COMP
    true          // shouldAccrue = true (flush pending rewards first)
);

Calculating Total Effective APY

For an agent evaluating whether to supply USDC to Comet, total effective APY has three components:

Effective APY = Supply APR + (COMP_per_year × COMP_price) / supplied_USDC − gas_cost_annualized

The COMP reward rate for suppliers in a Comet deployment can be read from the baseTrackingSupplySpeed parameter. Here is a complete rate calculator:

import { ethers } from 'ethers';

const COMET_ABI = [
  "function getSupplyRate(uint) view returns (uint)",
  "function getBorrowRate(uint) view returns (uint)",
  "function getUtilization() view returns (uint)",
  "function baseTrackingSupplySpeed() view returns (uint)",
  "function baseTrackingBorrowSpeed() view returns (uint)",
  "function totalSupply() view returns (uint)",
  "function totalBorrow() view returns (uint)",
];

const provider = new ethers.JsonRpcProvider(process.env.ETH_RPC_URL);
const comet = new ethers.Contract(
  '0xc3d688B66703497DAA19211EEdff47f25384cdc3',
  COMET_ABI,
  provider
);

async function calculateEffectiveAPY(compPriceUSD) {
  const utilization    = await comet.getUtilization();
  const supplyRatePerSec = await comet.getSupplyRate(utilization);
  const SECONDS_PER_YEAR = 365n * 24n * 3600n;

  // Supply APR (base, no compounding)
  const supplyAPR = Number(supplyRatePerSec * SECONDS_PER_YEAR) / 1e18;

  // COMP reward speed
  const trackingSpeed = await comet.baseTrackingSupplySpeed();
  const totalSupply   = await comet.totalSupply();
  const BASE_SCALE    = 1e6; // USDC has 6 decimals

  // COMP earned per USDC per year (tracking scale is 1e15)
  const compPerUSDCPerYear =
    (Number(trackingSpeed) * Number(SECONDS_PER_YEAR)) /
    (Number(totalSupply) / BASE_SCALE) /
    1e15;

  const compAPR = compPerUSDCPerYear * compPriceUSD;

  console.log(`Supply APR:    ${(supplyAPR * 100).toFixed(2)}%`);
  console.log(`COMP APR:      ${(compAPR * 100).toFixed(2)}%`);
  console.log(`Combined APY:  ${((supplyAPR + compAPR) * 100).toFixed(2)}%`);

  return { supplyAPR, compAPR, totalAPY: supplyAPR + compAPR };
}

calculateEffectiveAPY(45.00);
Note: COMP prices are volatile. Build yield comparisons with a conservative COMP price floor (e.g., 30-day EMA). Chasing COMP yield at peak COMP prices and then watching COMP drop 40% can turn an apparently positive-APY position sharply negative in real terms. Always stress-test your effective APY at COMP price −50%.

3. Optimal Supply and Borrow Strategies

Compound supports a spectrum of strategies depending on the agent's capital allocation objectives, risk tolerance, and time horizon. The three canonical approaches are: pure supply (yield generation), pure borrow (leverage), and the compound loop (recursive yield amplification).

Pure Supply Strategy

The simplest strategy: deposit USDC into the Comet USDC market and earn the current supply APR plus COMP rewards. No liquidation risk. Suitable for agents with a USDC treasury that would otherwise sit idle between other activities.

The Leverage Loop Strategy (Compound v2)

In v2, an agent can recursively supply and borrow the same asset (e.g., USDC) to amplify COMP rewards exposure. The loop: supply USDC, borrow a fraction back (up to the collateral factor, e.g., 75%), resupply the borrowed USDC, borrow again, and repeat. Each iteration multiplies both the interest paid and earned, and also the COMP accrued on both sides — net positive if COMP yield exceeds the borrow-minus-supply spread.

Loop multiplier = 1 / (1 − collateral_factor)    e.g., CF=0.75 → 4x theoretical max

Practical agents run 3–5 iterations to avoid excessive gas cost and keep health factor comfortable. Each iteration is a separate transaction in v2 (or can be batched via a custom entry contract).

// JavaScript: calculate optimal loop depth and expected APY
function calculateLoopStrategy(params) {
  const {
    initialCapital,    // USDC amount
    collateralFactor,  // e.g. 0.75
    supplyAPR,         // e.g. 0.04
    borrowAPR,         // e.g. 0.06
    compSupplyAPR,     // COMP earned on supply side
    compBorrowAPR,     // COMP earned on borrow side
    gasPerLoop,        // USD cost per loop iteration
    loops,             // number of iterations
  } = params;

  let totalSupply = 0;
  let totalBorrow = 0;
  let capital = initialCapital;

  for (let i = 0; i < loops; i++) {
    totalSupply += capital;
    const borrowed = capital * collateralFactor * 0.9; // 90% of max for safety buffer
    totalBorrow  += borrowed;
    capital       = borrowed;
  }

  const grossSupplyEarnings = totalSupply * (supplyAPR + compSupplyAPR);
  const grossBorrowCost     = totalBorrow * (borrowAPR - compBorrowAPR);
  const netYield            = grossSupplyEarnings - grossBorrowCost;
  const netAPY              = netYield / initialCapital;
  const healthFactor        = (totalSupply * collateralFactor) / totalBorrow;
  const annualGasCost       = gasPerLoop * loops * 52; // if rebalanced weekly

  return {
    totalSupply:    totalSupply.toFixed(2),
    totalBorrow:    totalBorrow.toFixed(2),
    netAPY:         (netAPY * 100).toFixed(2) + '%',
    healthFactor:   healthFactor.toFixed(2),
    annualGasCost:  annualGasCost.toFixed(2),
  };
}

// Example: $1,000 starting capital, 3 loops
console.log(calculateLoopStrategy({
  initialCapital: 1000,
  collateralFactor: 0.75,
  supplyAPR: 0.04,
  borrowAPR: 0.06,
  compSupplyAPR: 0.03,
  compBorrowAPR: 0.04,
  gasPerLoop: 8,
  loops: 3,
}));
// { totalSupply: '2359.38', totalBorrow: '1359.38', netAPY: '11.2%', healthFactor: '1.31' }
Risk: Loop strategies amplify liquidation risk proportionally. A 10% collateral price drop that would normally leave a single-supply position safe at 1.5x health factor can push a 3-loop position dangerously close to the liquidation threshold. Agents must implement hard health factor floors and emergency unwind logic. Never loop beyond the point where a 20% price drop would trigger liquidation.

4. Self-Repaying Loans Using Collateral Yield

Self-repaying loans are one of the most powerful primitives available to AI agents with long time horizons. The concept: supply a yield-bearing asset as collateral, borrow a stable asset against it, and let the collateral's native yield automatically pay down the debt over time. The agent receives immediate liquidity without ever making a manual repayment transaction.

The mechanics work most cleanly in Comet's ETH market using liquid staking tokens (LSTs) like cbETH, wstETH, or rETH as collateral:

  1. Agent supplies cbETH (Coinbase ETH, ~3.5% APY staking yield) to Comet ETH market
  2. Agent borrows WETH against it (up to 80% LTV on cbETH)
  3. cbETH accrues staking rewards, increasing its ETH redemption value over time
  4. As cbETH/ETH exchange rate rises, the position's health factor improves rather than degrades
  5. Effectively the borrow is repaying itself via staking yield — the agent's borrow-to-collateral ratio shrinks without any active intervention
Time to full repayment = (initial_borrow / collateral_value) / (staking_APY − borrow_APR)

For example, if an agent borrows WETH equivalent to 40% of their cbETH collateral value, and the net repayment rate (staking APY minus borrow APR) is 1% per year, full self-repayment takes 40 years — but the health factor starts at 2.0x and improves over time, making this practically risk-free for conservative borrow ratios. At a 20% initial borrow ratio and 2% net repayment rate, it takes 10 years — more realistic for long-horizon agents.

       {"name": "liquidateCollateralFactor", "type": "uint64"},

     ], "type": "tuple"}]},

def monitor_self_repaying_loan(w3, account_addr, staking_apy, borrow_apr):
    comet = w3.eth.contract(address=COMET_ETH, abi=COMET_ABI)

    borrow_wei  = comet.functions.borrowBalanceOf(account_addr).call()
    collat_wei  = comet.functions.collateralBalanceOf(account_addr, CBETH).call()
    asset_info  = comet.functions.getAssetInfoByAddress(CBETH).call()
    price_e8    = comet.functions.getPrice(asset_info[2]).call()

    cbeth_price = price_e8 / 1e8
    borrow_eth  = borrow_wei / 1e18
    collat_eth  = (collat_wei / 1e18) * cbeth_price

    borrow_hf       = (collat_eth * (asset_info[4] / 1e18)) / borrow_eth
    liquidation_hf  = (collat_eth * (asset_info[5] / 1e18)) / borrow_eth
    net_repay_rate  = staking_apy - borrow_apr

    years_to_repay = (borrow_eth / collat_eth) / net_repay_rate if net_repay_rate > 0 else float('inf')

    print(f"Borrow:           {borrow_eth:.4f} ETH")
    print(f"Collateral:       {collat_eth:.4f} ETH (cbETH @ {cbeth_price:.4f})")
    print(f"Borrow HF:        {borrow_hf:.2f}")
    print(f"Liquidation HF:   {liquidation_hf:.2f}")
    print(f"Net repay rate:   {net_repay_rate*100:.2f}%/yr")
    print(f"Self-repay est:   {years_to_repay:.1f} years")

    return {"borrow_eth": borrow_eth, "collateral_eth": collat_eth,
            "health_factor": borrow_hf, "years_to_repay": years_to_repay}

5. Compound Governance Participation for COMP Holders

COMP is not just a yield token — it is a governance token granting proportional voting power over core protocol parameters. Agents holding COMP can participate in governance directly or delegate their votes to specialized governance agents. For agents operating at scale, governance participation is also an alpha generation surface: parameter changes directly affect position profitability.

Governance Architecture

Compound uses a modified OpenZeppelin Governor Bravo implementation. Key parameters as of early 2026:

  • Proposal threshold: 25,000 COMP (must hold or have delegated to your address)
  • Quorum: 400,000 COMP votes in favor required for passage
  • Voting period: approximately 3 days (~19,710 blocks at 13s/block)
  • Timelock delay: minimum 2 days after proposal passes before execution

Proposals that materially affect agents: collateral factor changes, interest rate model parameter adjustments, reward speed modifications, new asset listings, and protocol pause/unpause actions. A 2-day timelock on all changes means agents have at least 48 hours to respond after a proposal executes — more if the voting period is included.

Delegating and Voting

const COMP_TOKEN = '0xc00e94Cb662C3520282E6f5717214004A7f26888';

// Step 1: delegate voting power to self (must be done once)
const currentDelegate = await comp.delegates(signer.address);
if (currentDelegate !== signer.address) {
  await (await comp.delegate(signer.address)).wait();
  console.log('Delegated to self');
}

const votes = await comp.getCurrentVotes(signer.address);
console.log(`Voting power: ${Number(votes) / 1e18} COMP`);

// Step 2: vote on an active proposal
async function voteOnProposal(proposalId, support, reason) {
  // support: 0=Against, 1=For, 2=Abstain
  const state = await gov.state(proposalId);
  if (state !== 1n) {
    console.log(`Proposal ${proposalId} is not in Active state (state=${state})`);
    return;
  }
  const tx = await gov.castVoteWithReason(proposalId, support, reason);
  await tx.wait();
  console.log(`Voted ${support === 1 ? 'For' : 'Against'} on proposal ${proposalId}`);
}

// Monitor upcoming proposals
gov.on('ProposalCreated', (id, proposer, targets, values, signatures, calldatas, start, end, description) => {
  const sensitiveKeywords = ['collateralFactor', 'setBaseTracking', 'pause', 'setBorrowRate'];
  const sensitive = signatures.some(sig => sensitiveKeywords.some(k => sig.includes(k)));
  if (sensitive) {
    console.warn(`ALERT: Governance proposal ${id} may affect agent positions. Description: ${description.slice(0, 120)}`);
  }
});

Governance Alpha: Pre-Positioning Around Parameter Changes

Sophisticated agents monitor the Compound governance forum and proposal queue to identify upcoming parameter changes. If a proposal to increase the USDC Comet supply rate cap from 8% to 12% is approaching passage, agents can pre-supply USDC to capture the higher rate from the first block after execution. Similarly, reductions in COMP reward speeds signal that positions relying heavily on COMP APR should be rebalanced before the effective block.

6. Multi-Collateral Strategies Across Compound Markets

Agents with diversified crypto holdings can optimize across Compound v2's multi-collateral pool or across multiple Comet deployments simultaneously. Different collateral assets carry different risk-reward profiles, and mixing them achieves a superior portfolio-level risk-adjusted return compared to single-asset strategies.

V2 Multi-Collateral Optimization

In v2, the Comptroller calculates borrowing power as the weighted sum of all supplied collateral. An agent supplying ETH (CF: 82%), WBTC (CF: 70%), and USDC (CF: 80%) simultaneously has its total borrowing capacity calculated as the sum of each position multiplied by its collateral factor. The optimal multi-collateral allocation minimizes liquidation probability (by diversifying price risk) while maximizing total COMP reward surface area.

Cross-Chain Deployment Arbitrage

An advanced agent may run simultaneous positions across Ethereum mainnet Comet USDC, Arbitrum Comet USDC, and Base Comet USDC. Each deployment has independent utilization curves and COMP reward allocations — cross-chain APR arbitrage is genuinely available and mechanically straightforward for agents with cross-chain wallets.

// Monitor multiple Comet deployments for best supply rate
const COMET_DEPLOYMENTS = [
  { chain: 'ethereum', address: '0xc3d688B66703497DAA19211EEdff47f25384cdc3', rpc: process.env.ETH_RPC },
  { chain: 'arbitrum',  address: '0x9c4ec768c28520B50860ea7a15bd7213a9fF58bf', rpc: process.env.ARB_RPC },
  { chain: 'base',      address: '0xb125E6687d4313864e53df431d5425969c15Eb2', rpc: process.env.BASE_RPC },
  { chain: 'polygon',   address: '0xF25212E676D1F7F89Cd72fFEe66158f541246445', rpc: process.env.POLY_RPC },
];

const RATE_ABI = [
  "function getSupplyRate(uint utilization) view returns (uint64)",
  "function getUtilization() view returns (uint)",
];
const SECONDS_PER_YEAR = 365 * 24 * 3600;

async function getBestDeployment() {
  const results = await Promise.all(
    COMET_DEPLOYMENTS.map(async ({ chain, address, rpc }) => {
      const provider = new ethers.JsonRpcProvider(rpc);
      const comet    = new ethers.Contract(address, RATE_ABI, provider);
      try {
        const util    = await comet.getUtilization();
        const rate    = await comet.getSupplyRate(util);
        const apr     = Number(rate) * SECONDS_PER_YEAR / 1e18;
        return { chain, address, apr, utilization: Number(util) / 1e18 };
      } catch (e) {
        return { chain, address, apr: 0, error: e.message };
      }
    })
  );

  results.sort((a, b) => b.apr - a.apr);
  console.log('=== Compound USDC Supply APR by Chain ===');
  results.forEach(r => {
    console.log(`${r.chain.padEnd(10)} ${(r.apr * 100).toFixed(2)}%  util=${(r.utilization * 100).toFixed(1)}%`);
  });
  return results[0];
}

8. Compound III (Comet) Base Asset Model — Rate Mechanics

Understanding Comet's interest rate math lets agents predict rate changes and pre-position ahead of them. The model uses a kinked curve with four core parameters per market: supplyKink, borrowKink, and low/high slope parameters for each side.

UtilizationSupply APR (est.)Borrow APR (est.)Spread
0%0.00%1.00%1.00%
50%2.10%3.50%1.40%
80% (kink)5.20%6.80%1.60%
90%8.40%13.50%5.10%
95%11.20%21.00%9.80%
99%14.50%38.00%23.50%

The dramatic spread above the kink incentivizes repayment when the market is overly borrowed and creates attractive supply rates for new capital inflow. Agents monitoring utilization crossing the kink threshold can predict imminent rate spikes and act accordingly: pre-supply to capture elevated rates, or pre-repay to avoid expensive borrow costs.

Absorption and Bad Debt Recovery

Comet introduces a novel absorption mechanism for bad debt that creates an earning opportunity for keeper agents. When a position becomes undercollateralized, any address can call absorb(absorber, accounts[]) to absorb the position into the protocol's reserves. The absorber receives a small incentive paid in the base asset. The protocol then sells the absorbed collateral via buyCollateral() — available to any agent at a slight discount.

// Compound III keeper: absorb underwater accounts and buy discounted collateral
const COMET_KEEPER_ABI = [
  "function isLiquidatable(address account) view returns (bool)",
  "function getCollateralReserves(address asset) view returns (uint128)",
  "function quoteCollateral(address asset, uint baseAmount) view returns (uint)",
  "function absorb(address absorber, address[] calldata accounts)",
  "function buyCollateral(address asset, uint minAmount, uint baseAmount, address recipient)",
];

async function keeperRound(comet, absorber, accountList, collateralAsset) {
  // 1. Find liquidatable accounts
  const flags = await Promise.all(accountList.map(a => comet.isLiquidatable(a)));
  const liquidatable = accountList.filter((_, i) => flags[i]);

  if (liquidatable.length === 0) {
    console.log('No liquidatable accounts this round.');
    return;
  }

  console.log(`Absorbing ${liquidatable.length} accounts...`);
  await (await comet.absorb(absorber, liquidatable)).wait();

  // 2. Check collateral reserves now available at discount
  const reserves = await comet.getCollateralReserves(collateralAsset);
  if (reserves === 0n) return;

  // 3. Quote and buy
  const baseNeeded = await comet.quoteCollateral(collateralAsset, reserves);
  console.log(`Buy ${reserves} collateral for ${baseNeeded} base asset`);
  await (await comet.buyCollateral(
    collateralAsset,
    reserves * 98n / 100n,  // 2% slippage tolerance
    baseNeeded,
    absorber
  )).wait();
  console.log('Keeper round complete.');
}

9. Liquidation Mechanics and Health Factor Management

Liquidation risk is the primary operational hazard for leveraged Compound positions. Understanding the precise mechanics — and building robust automated health factor management — is non-negotiable for any long-running agent deployment.

Comet Liquidation Threshold

A Comet position becomes liquidatable when:

∑(collateral_i × liquidateCollateralFactor_i × price_i) < borrow_balance × price_base

Key contrast with v2: Comet's absorb mechanism transfers the entire underwater position to the protocol — the borrower loses all their collateral beyond the debt owed. There is no partial liquidation with a bonus. This makes Comet liquidations more punishing for borrowers but mechanically simpler for keeper agents to implement.

11. Automating Positions: Rebalancing and Compounding Rewards

Every Compound strategy requires automating at least three lifecycle events: periodic rebalancing (health factor maintenance), reward compounding (COMP claim and reinvest), and position migration (when better yields appear elsewhere). Manual position management is not viable at agent scale.

Rebalancing Triggers

  • Health factor drops below a configured floor (e.g., 1.3x on borrow CF basis)
  • Price deviation of a collateral asset exceeds 5% from entry price
  • Supply APR on Compound drops more than 1.5% below competitor protocols
  • COMP price changes more than 20% (affecting net APY calculations)
  • Compound governance proposal passes that changes interest rate parameters
  • Utilization crosses the kink threshold in either direction

Gas-Optimal COMP Compounding

COMP rewards should be claimed and reinvested rather than held passively. The optimal compounding frequency balances gas cost against yield lost to unclaimed rewards. For a position earning $50/month in COMP, claiming weekly ($8 gas x 4 = $32/month) eats 64% of yield. Claiming monthly eats only 16%. The gas-optimal interval is derived from the square root formula:

Optimal claim interval (days) = sqrt(2 × gas_cost_USD / daily_COMP_value_USD) 
# Python: determine if now is optimal time to claim COMP
import math, time

def optimal_claim_interval_days(gas_cost_usd, daily_comp_value_usd):
    if daily_comp_value_usd <= 0:
        return float('inf')
    return math.sqrt(2 * gas_cost_usd / daily_comp_value_usd)

def should_claim(last_claim_ts, gas_cost_usd, daily_comp_value_usd):
    interval   = optimal_claim_interval_days(gas_cost_usd, daily_comp_value_usd)
    elapsed    = (time.time() - last_claim_ts) / 86400  # days
    return elapsed >= interval

# Example: $12 gas, earning $2/day in COMP
interval = optimal_claim_interval_days(12, 2)
print(f"Optimal claim interval: {interval:.1f} days")  # ~3.5 days

# Example: $30 gas, earning $0.50/day in COMP
interval = optimal_claim_interval_days(30, 0.5)
print(f"Optimal claim interval: {interval:.1f} days")  # ~11 days

  const receipt  = await (await comet.withdraw(USDC, balance)).wait();
  const finalBal = await usdc.balanceOf(wallet.address);
  console.log(`Closed. Received ${Number(finalBal) / 1e6} USDC. Tx: ${receipt.hash}`);
}

13. Risk Analysis: Governance, Oracle, and Liquidity Risks

Compound is one of DeFi's most battle-tested protocols, but operating on it programmatically introduces systemic risks that must be explicitly modeled in any serious agent deployment. The three primary risk categories are governance risk, oracle risk, and liquidity risk.

Governance Risk

Compound is governed by COMP token holders with no veto from the Compound Labs team. Any parameter — collateral factors, interest rate models, supported assets, reward distributions, and protocol fees — can be changed by a successful governance proposal. Historical governance actions include sudden collateral factor reductions (which instantly changed health factors for all active borrowers), addition of risky assets, and changes to liquidation incentives.

  • Collateral factor reduction: A 5% CF cut on ETH instantly reduces borrowing power for all ETH-collateralized positions. Agents with tight health factors face immediate liquidation risk with zero additional market movement required.
  • COMP reward speed changes: Governance can reduce or eliminate COMP rewards with only a 2-day timelock. Positions premised on COMP APR become uneconomic overnight.
  • Market pause: A pause multisig guardian can freeze borrowing, minting, and liquidations. A paused borrow market may prevent repayment, locking positions in a frozen state.
  • Upgrade risk: Proxy upgrades to Comet contracts can introduce bugs. Monitor the proposal queue for scheduled upgrades.
Mitigation: Subscribe to Compound governance alerts via Tally, Boardroom, or direct event monitoring of the Governor contract's ProposalCreated events. Set automated alerts for any proposal touching collateral factors or reward speeds on markets where your agent holds active positions. When a relevant proposal enters the voting period, immediately calculate its impact on your health factor if it passes.

Oracle Risk

Compound v3 (Comet) relies on Chainlink price feeds to determine collateral values and trigger liquidations. Residual oracle risks include:

  • Feed staleness: Chainlink feeds have heartbeat thresholds (1 hour for major assets, 24 hours for stablecoins). Stale prices during market disruptions can delay liquidations, creating bad debt accumulation risk.
  • Flash crash exposure: Temporary price drops on volatile collateral assets during the oracle heartbeat window can bypass liquidation protection briefly, allowing positions to accumulate unreported losses.
  • LST depeg events: Agents using cbETH or wstETH as collateral are exposed to LST depeg scenarios. A 10% cbETH/ETH depeg (as observed with stETH in June 2022) reduces collateral value proportionally, instantly degrading health factors across all cbETH-collateralized positions simultaneously.

Liquidity Risk

Compound market liquidity risk manifests in two forms: withdrawal queue risk (inability to exit a supply position when utilization is near 100%) and borrow availability risk. When Comet USDC utilization approaches 100%, withdraw() may revert because there is insufficient idle USDC in the contract. Agents holding supply positions should pre-exit when utilization exceeds 92% if immediate liquidity is required.

# Python: liquidity assessment before exiting a Comet supply position
def assess_exit_liquidity(w3, comet_address, required_usdc):
    ABI = [
        {"name": "getUtilization", "type": "function", "inputs": [], "outputs": [{"type": "uint256"}]},
        {"name": "totalSupply",    "type": "function", "inputs": [], "outputs": [{"type": "uint256"}]},
        {"name": "totalBorrow",    "type": "function", "inputs": [], "outputs": [{"type": "uint256"}]},
    ]
    comet         = w3.eth.contract(address=comet_address, abi=ABI)
    util          = comet.functions.getUtilization().call() / 1e18
    total_supply  = comet.functions.totalSupply().call() / 1e6
    total_borrow  = comet.functions.totalBorrow().call() / 1e6
    available     = total_supply - total_borrow

    print(f"Utilization:  {util*100:.1f}%")
    print(f"Available:    ${available:,.0f} USDC")
    print(f"Required:     ${required_usdc:,.0f} USDC")

    if available < required_usdc:
        print("BLOCKED: Insufficient liquidity. Wait for borrows to repay or rates to spike.")
        return False
    elif util > 0.90:
        print("CAUTION: High utilization. Exit now before more borrows arrive.")
        return True
    return True
